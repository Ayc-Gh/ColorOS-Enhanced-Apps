## 补充核对：与并行部署试验的关联

已核对用户提供的并行部署记录中的实际命令和输出，公开摘要不包含聊天标识。本轮审计期间，另一会话正在同一手机上执行 Root chroot／挂载试验。因此，这段系统结果受到并行环境修改影响，不能当作隔离的模块回归来归因。

**artd／包管理阻塞与该挂载试验有很强关联，完整根因尚未证明。** 那边记录 `mount -o rprivate / /` 留下 PID 25793、26164 两个 D 状态任务，栈停在 `lock_mount`；读取挂载信息的 awk（PID 26620）也停在 `m_start`。宿主 mountinfo 中出现多组该 chroot 的 proc/dev/pts 挂载。本轮同期记录 init 停在 `m_start → seq_read_iter`、控制队列溢出，PackageManager 等待未能启动的 artd。重启后两边的阻塞均解除。

上游 Linux 6.1 中，挂载信息迭代器 `m_start` 读取 `namespace_sem`，`lock_mount` 经 `namespace_lock` 获取同一信号量的写锁，支持“共同挂载锁阻塞”的机制解释。但缺少当时锁持有者的完整采样与隔离复现，不能断言每条 artd ENOENT 都由某条挂载命令直接造成。[Linux 6.1 源码](https://github.com/torvalds/linux/blob/v6.1/fs/namespace.c)

**qti-testscripts 暂无直接关联证据。** 本轮 16:52:22 的 PID 6821 已对应到该服务；但部署会话开始前的 15:19:26、03:17:55，历史 crash 缓冲中已有同形态的 init 子进程 SIGABRT。旧 PID 缺少服务映射，因此只能判断类似开机崩溃早已存在，不能把旧记录也直接认定为 qti-testscripts，或把本次事件直接归咎于部署。

重启归属修正：用户在另一会话允许重启，随后由那边执行 ADB 重启，本审计会话未发送重启命令。那边随后改用 util-linux 的递归私有挂载，增加 shared 挂载检查，并记录重启后宿主测试挂载数为 0。这些是另一会话的恢复证据，本次交叉核对没有操作手机。

本轮清理结论仅覆盖本模块审计创建的探针、测试应用、媒体和诊断副本；另一会话为部署 Harness 创建的独立目录不属于本轮清理范围，未被本任务删除。脱敏交叉证据位于 `related-chroot-thread-evidence.json`。ENV-1 应归类为“并行挂载试验强相关的环境阻塞”，不能认定为 2.1.6 引入的缺陷。

## 优先处理的问题

### P1 / ENV-1：系统包管理等待 artd，卸载阻塞

清理第一个测试应用时，卸载超过 45 秒未返回；随后系统记录 PackageManager 处理线程阻塞 150 秒，产生一次预看门狗诊断。线程栈为 `DeletePackageHelper → clearAppProfiles → getArtd → ServiceManager.waitForService`。

内核日志明确记录原生 `artd` 多次启动后退出 127，并报告 `cannot execv('/apex/com.android.art/bin/artd'): No such file or directory`。与此同时，ADB 根环境可以看到该文件。后来 init 处于 D 状态，内核栈停在 `m_start → seq_read_iter`，服务控制队列溢出。**已确认阻塞链路；尚未确认文件可见性/执行环境异常的完整根因，也没有证据直接归因于本模块。** 并行挂载试验的强关联证据见上文补充核对。

用户先在本会话要求等待；交叉核对后确认，另一会话获得用户授权并执行了 ADB 重启。本任务没有发出重启命令。重连后读取到新启动标识和 `reboot,shell` 原因；原生 artd 启动、Binder 注册成功，后续 10 个测试应用均正常卸载。重启后的系统、SystemUI、声音宿主、audioserver PID 持续稳定。当前操作已恢复，不能把一次恢复当作永久修复。

建议后续专项核对 ART/APEX 的执行环境与 Root 环境，再决定是否需要模块修改。证据：`cleanup-package-manager-selected-stacks.txt`、`cleanup-service-failure-dmesg.txt`、`native-prewatchdog-original.trace`、`artd-recovery.json`。

### P2 / UI-1：声音页沿用上次启动的失败提示

重启后关闭声音增强时，页面仍显示旧的“未生效，原生范围已恢复：Audio command failed (127)”。对应持久状态时间为上次启动的 `5160052 ms`，当前 lease 为 disabled。正常从正式界面开启后立即恢复健康，再关闭可得到新的原生恢复状态。

源码 `SoundController.state()` 只对“已生效”检查时间与版本新鲜度，其他错误文案会直接返回，因此旧失败提示可以跨重启保留。建议将失败提示也纳入启动周期／时效校验，避免把历史错误显示为当前状态。本次刷新了状态，**未修改产品代码**。证据：`sound-stale-error-after-reboot.json/.xml`。

### P2 / ENV-2：原生 qti-testscripts 启动时崩溃

重启后的 **16:52:22**，crash 缓冲出现 PID 6821、进程名 init 的 SIGABRT。内核日志将该 PID 对应到 **qti-testscripts** 服务，随后确认服务收到 SIGABRT；crash_dump 的 ptrace 被 SELinux 拒绝，未生成完整 tombstone。它不是 PID 1，也不是 SoundPolicyRoot。触发原因尚未查明；系统完成启动，后续清理和后台观察正常。
