# OPPO 互联电脑投屏：实机链路与适配

设备：OPPO Find X7 Ultra / PHY110，ColorOS 17.0.0.100 CN01、Android 17 API 37，SM8650。分析日期：2026-11-12。

## 实际经过哪些组件

本次在手机已向 Windows 的“OPPO 互联 / 手机画面”投屏时读取系统服务、MediaProjection、虚拟显示和编码日志，观察到：

```text
Windows OPPO 互联 / phoneCast.exe
                 ↕ 互联会话
com.oplus.linker（OPSynergy，17.7.30）
  PcCastEngineService / CastCoreService
                 ↓ 绑定 CastService
com.oplus.cast（HeyCast，屏幕投屏，17.0.017）
                 ↓ MediaProjection / ODMF / WebRTC
虚拟显示 10000，镜像手机显示 0
                 ↓ Qualcomm 硬件 H.264
电脑“手机画面”
```

`dumpsys activity services` 中 CastService 的客户端是 `com.oplus.linker`，绑定动作为 `com.oplus.cast.service.command`；`dumpsys media_projection` 中捕获拥有者为 `com.oplus.cast`，uid 10145，镜像显示 0，目标虚拟显示 10000。虚拟显示尺寸为 1440×3168、60 Hz。

独立的 `com.coloros.sharescreen`（ShareScreen 17.0.35）没有在此会话中运行或持有捕获。相关共享设置主要操作另一条 ORTC 链路，不能直接改善当前 OPPO 互联电脑镜像。按用户明确选择，1.1.0 不加入该组件的功能。

电脑互联的连接、授权和认证仍使用系统流程。新增模块作用域只有 `com.oplus.cast`；原有系统作用域用于 1.0.0 的分屏、小窗和截图功能。

## 基线

实机编码日志中观察到：输入与编码尺寸 1440×3168，videoSendFps=60，mimeType=video/H264，encoderImplementation=c2.qti.avc.encoder，动态码率目标约 12,000,000 bps。静止画面实际编码帧数可以很低，不能据此把配置 60 帧写成“每秒持续编码 60 张”。

手机物理屏幕为 1440×3168，物理 density=640，用户的有效 density override=560。系统已经能够进行原生分辨率的硬件投屏，没有命中针对部分其他机型的降级名单，因此不需要默认启用机型伪装或全部能力绕过。

## 功能实现与本机接口

核对对象为参考模块 16.14.1912（1455）。其 `heycast` 功能在反编译别名 `yx3`，通过 DexKit 的字符串、参数和返回类型寻找方法。公开源码标签不能直接代表安装版。

| 功能 | 策略方式 | 本机 HeyCast 17.0.017 对应入口 |
| --- | --- | --- |
| 码率表、自定义、低带宽 | 改写返回的两个 kbps 整数；均衡至少 8000/16000，高档至少 20000/32000 | `k2.c0.e(z2.l, boolean)` → `android.util.Pair` |
| 游戏场景 | 从启动 Bundle 的 cast_scenario=1 保存状态 | `k2.g.Q(DeviceInfo, Bundle)` |
| 帧率 | 提高 codec rect 的帧率上限并改写 pickFps 的请求 | `k2.c0.n(int,int,int)`、`j(int)` |
| 分辨率 | 修改 custom display 输入；上游含固定 1920×1080、3120×1440 预设 | 本机 `k2.c0.i()` 选好格式后，对编码与捕获尺寸一起做等比上限处理 |
| DPI | 上游强制返回 640 | 基类 `CastDisplayManager.r(z2.l)` 和电脑专用 `k2.b0.B(int)`；电脑分支读取实际输入的有效 DPI |
| 机型降级 | 修改能力 setter 的低帧率或跳过按机型的降级方法 | `a3.a.f(a3.a$a)` |
| 硬件能力 | 跳过部分机型覆盖 | 在机型策略前保存 Android 枚举结果，在 `a3.a.c()` 返回后恢复这组实际能力 |
| 最终参数诊断 | — | 仅在屏幕投屏进程观察视频 encoder 的 `MediaCodec.configure` |

这些混淆名称按本机实际 APK 的方法体、签名和字符串逐一核对，挂钩前检查类型与参数数量；缺失的接口单独跳过。本机安装 11 个投屏挂钩。对应用内部的相关调用方法及构造路径先执行 deoptimize，处理 OEM 编译内联；配置监听器保留强引用以同步运行中的进程。没有向系统或其他 APP 注入通用的编码参数改写，也没有增加 DexKit 运行依赖。

## 本机优化

- 码率明确区分 kbps（应用策略）与 bps（编码器日志），避免相差 1000 倍。自定义值优先于档位、低带宽和游戏策略，修正同时启用时的覆盖歧义。
- 分辨率按物理屏幕和内容原比例计算。1080 档在本机为 1080×2376，1440 / 原生档为 1440×3168；横屏交换宽高。结果对齐偶数，不拉伸、不把较小的协商结果强行放大。
- 帧率先查询 Android 硬件 AVC 编码器对当前尺寸的支持，再限制请求。电脑接收能力、网络和内容变化仍会影响实际发送帧率；90 / 120 是可选请求，不能承诺实际到达。
- DPI 跟随实际有效值，兼容这台手机的 560 override，不改变手机系统 DPI。
- 均衡建议为至少 8–16 Mbps、60 帧、原生协商分辨率和跟随当前 DPI。高级机型 / 硬件 / 游戏选项默认关闭。
- 总开关关闭后，在新投屏会话中恢复系统协商；“仅恢复投屏默认设置”不会清除原分屏、小窗和截图设置。

## 验证记录

Release 构建、签名校验和静态检查通过（0 错误、9 警告）。17 项独立参数检查通过，覆盖 kbps 单位、档位和自定义优先级、无降级和无放大、PHY110 横竖屏比例、未知屏幕回退、硬件帧率上限。

实机验证通过：

| 场景 | 实际结果 |
| --- | --- |
| 开启优化，1080 等比档，自定义 18 Mbps，DPI 跟随 | 系统虚拟显示为 1080×2376、60 Hz、DPI 560；WebRTC 实际分配器最小/最大为 18000/18000 kbps |
| 同一进程关闭优化并重新投屏 | 恢复 1440×3168、60 Hz、DPI 640；流分配器恢复原生 12000/12000 kbps，18 Mbps 配置不再生效 |
| 最终签名版本，应用本机建议设置并重新投屏 | 1440×3168、60 Hz、DPI 560；流分配器为 12000/16000 kbps；自定义码率已关闭 |
| 设置和作用域 | 仅增加 com.oplus.cast；原分屏、小窗、截图设置保留；独立屏幕共享和连接认证没有改写 |

12/16 Mbps 是本次原生尺寸会话协商后的范围：均衡档的 8/16 是下限，不把原来高于 8 的最小值强行降到 8。流分配器、应用策略表、初始编码器参数及实际发送速率属于不同阶段，不能混为一项。虚拟显示 60 Hz 和请求 60 帧不代表静止页面每秒持续发送 60 张图；实际帧率、码率会按画面和网络自适应。

90/120 帧、全部高级硬件/游戏组合和其他 ROM 尚未逐项实测。横屏比例已做独立参数检查，未以完整横屏投屏会话作实测声明。正式交付保留建议的 60 帧、原生协商尺寸、均衡码率、DPI 跟随；高级项关闭。诊断日志与框架开发者/Hook 调试模式在验证后关闭。脱敏结果见 `evidence/cast-1.1.0/validation.json`。

硬件 DRM 内容、独立屏幕共享通话及音频处理不在此次扩展范围内。
