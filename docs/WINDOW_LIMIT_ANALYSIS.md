# 投屏应用与贴边数量限制定位

日期：2026-11-13。设备：PHY110，ColorOS 17.0.0.100(CN01)。电脑：OPPO 互联 17.20.3。此记录保留初步定位与电脑单端失败实验，并补充后续两端配套测试。正式整合模块未因投屏实验更新，电脑安装文件未改写。两端实测详情见 [多路配套测试记录](PAIRED_CAST_TEST.md)。

## 贴边应用

已找到独立于小窗数量的数量控制：系统 `FloatHandleController.getLimitMaxFloatNum()` 读取 `mLimitMaxFloatNum`。初始化在手机上设置为 2，部分具有全景工作台能力的非手机设备设置为 5。

添加贴边任务时，`updateInfoMapForAdd()` 比较现有数量与这个上限；相等时移除最早的记录，将对应任务恢复到全屏，再加入新任务。因此本机的两应用限制有明确的软件修改入口。

可在现有“分屏与小窗”入口增加独立的贴边数量设置，通过系统框架作用域覆盖数量 getter。应先验证 4–5 个任务的排列、展开、回收和切换；代码中的非手机五任务分支不能替代手机布局实测。现有贴边保活许可与这个数量上限是不同判断。

本次可行性分析时的 1.4.1 没有覆盖此 getter，已有“小窗数量”设置不控制贴边记录数量。后续 1.4.2 已新增独立设置，实现与验证范围见 [贴边数量记录](EDGE_COUNT.md)；本节保留定位当时的证据。

## 电脑投屏的应用窗口

用户指的是电脑 OPPO 互联同时打开的手机应用窗口。它与手机本地小窗及贴边数量使用不同流程。

手机互联本体 `com.oplus.linker` 的 `MultiplexControl.getSupportMultiplex()` 根据接收端、无线频段及初始化策略返回能力值。该版本包含 Windows=2 的初始化表，同时有 5 GHz 返回 3、策略值最大裁为 3 的代码。

**实际连接日志在 02:40 返回 3**，记录接收端为 Windows，Wi-Fi 频率为 5180 MHz。因此不能仅凭初始化表中的数字 2，认定当前受限原因就是该分支。`MirageSceneImpl` 中以能力值创建 HashMap 的构造参数只是初始容量，也不能单凭它认定已经实施硬上限。

电脑 `phoneCast.exe` 存在窗口数量检查，以及达到上限时关闭已有应用窗口的路径。对当前二进制的只读反汇编还确认：窗口管理初始化将参数 5 传入数量 setter；setter 把正整数写入对象字段。因此当前电脑程序也不能简单描述成写死两窗口。5 是初始化管理值，不代表五路画面已被端到端实测支持。

本轮从电脑入口发起过第三个“设置”应用窗口请求。桌面出现相应窗口，但窗口标题和缓存画面不足以证明第三路应用持续运行；随后读取的手机任务与虚拟显示状态未能证明三个不同应用同时持续显示。没有将这个请求记为解除成功。

上述是初步定位结果。后续用户明确补充：五个窗口可以保留，但只能同时活动两个应用。进一步核对及实验如下。

## 电脑端活动数量对照实验

电脑 `WindowControl` 保存正在投屏的列表；实机读取的列表大小为 2。新建应用及恢复暂停应用的流程存在达到 2 时停止最早一路的判断，停止后可保留窗口并显示继续投屏遮罩。它与管理五个窗口的初始化值不同。

针对当前二进制，已关联到三处候选比较指令：RVA `0x6956e`、`0x76a80`、`0x7724b`。实验仅将正在运行进程中的三个比较值临时从 2 改为 5，没有修改磁盘上的 EXE。三个修改点均进行了写入后回读核验。

**实验未通过。** 电脑列表曾短暂读到 3，但用户实测仍只有两个应用活动，并出现打开第三个窗口时第一个窗口直接关闭的副作用。因此这个瞬时列表值不能作为三路投屏成功证据，三个比较值的修改也不能作为可交付方案。

手机互联本体中还找到独立的通道分配限制：

1. `CastSceneManager` 收到电脑请求后，将应用投屏的 `rtspPort` 设置为 7237。电脑请求中的 `port` 被用作 `signalServerPort`，不是这个应用通道选择项。
2. `CastSceneImpl.startMirageCast()` 调用 `CommonUtils.saveUsePort()`，将返回值用于输入路由及后续启动。
3. `saveUsePort()` 首先使用传入的 7237；被占用时改用固定的 7238；两者均占用时调用 `clearAllPort()`，随后回用原端口。当前这条路径没有分配第三个独立应用通道。

这说明手机公布的能力值 3、电脑的五窗口管理值，都不能替代实际应用通道分配。移除电脑的预先暂停后，端口回用会与已有会话冲突；该机制与此次较早窗口被关闭的现象吻合，具体关闭回调仍需两端联调追踪，未单独截获为完整因果链。

**当前结论：仅修改电脑端不足以解除本机两应用同时活动的限制。** 配套方案至少需要处理电脑的新建/恢复策略、手机的通道分配及回收、端口与输入路由映射，并验证多路编码和实际画面刷新。当前手机请求处理路径会自行设置应用通道，仅修改电脑请求中的 `port` 无法达到目的；不能仅将某个能力值改大后标记成功。

正式整合模块只在 `com.oplus.cast` 中调整投屏参数；修改上述互联本体逻辑需新增 `com.oplus.linker` 对应 Hook 与作用域。后续已使用独立临时模块实现配套实验：三路内容与操作对照通过，四路表现取决于应用负载，五路出现卡顿及自动关闭。这些结果没有证明五路稳定可用，正式版尚未加入多路功能。

电脑单端实验结束时的恢复核验：三处内存比较值已全部恢复为 2，电脑安装文件 SHA-256 保持不变；未交付或启用永久补丁。实验导致关闭的窗口需要重新打开。失败实验脚本的 apply 操作已禁用，避免误作正式解除工具使用。后续两端配套实验的最终恢复状态另见配套记录。

结果摘要见 [电脑端实验与恢复记录](evidence/desktop-multi-active-20261113/validation.json)。

## 实现边界

- 贴边：1.4.2 已新增独立设置，验证范围见 [贴边数量记录](EDGE_COUNT.md)。
- 电脑应用投屏：电脑单端实验失败；两端配套已验证三路，四路存在负载相关的不稳定，五路失败。尚未并入正式版或交付永久电脑补丁。
- 不应将两项绑定到现有“小窗数量”，也不应标注为无限数量。多路编码、显示与内存仍有实际负载限制。
